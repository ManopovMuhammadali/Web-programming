CASE STUDY 01 / WEEK 06

API Explorer.

Connecting a browser interface to external data.

Individual coursework

THE PROJECT

Making external data useful.

I built a small API playground containing six separate exercises. Each exercise requests data from an external service and displays the response in the browser.

The project covers more than making a request. It also practises asynchronous JavaScript, response handling, loading messages, error feedback and creating interface elements from returned data.

JavaScript Fetch API JSON Async / Await DOM
Open live project ↗ Inspect source code ↗
01 / FEATURES

What it does

  • Random Joke Fetcher — retrieves a joke from an external API.
  • Posts — loads five sample posts from JSONPlaceholder.
  • Seoul Weather — displays current weather data from Open-Meteo.
  • Random Users — displays four generated profiles.
  • Pokédex — searches Pokémon by name or number.
  • Country Table — sorts country data and displays the first twenty results.
02 / IMPLEMENTATION

How I handled requests

I used a shared helper function to avoid repeating the same basic request and response-checking logic in every exercise. 

async function getJSON(url) {
  const response = await fetch(url);

  if (!response.ok) {
    throw new Error(
      "Request failed: " + response.status
    );
  }

  return response.json();
}

The individual exercises use try and catch to handle failures and update their own output areas.

03 / ENGINEERING DECISIONS

Why I structured it this way

  • One request helper: centralises the basic HTTP status check and JSON parsing.
  • Async / await: keeps asynchronous request logic readable.
  • DOM methods: several exercises use createElement(), textContent and append() to render returned data.
  • Separate output areas: each exercise can display its own loading state, result or error message.

WHAT I LEARNED

A request can fail even when the JavaScript syntax is correct. I learned to check the HTTP response, parse JSON, handle errors and update the page after asynchronous work.

NEXT ITERATION

I would add request cancellation, more consistent button loading states and caching. I would also avoid downloading an entire country dataset when only a small subset is required.

CASE STUDY 02 / WEEK 07

Open Library Book Finder.

Turning a search query into useful book results.

Individual coursework

THE PROJECT

A search interface backed by real data.

I created a book search page that sends a query to the Open Library Search API and displays matching books as individual result cards.

Each result can show a title, an author, a first publication year and a cover image when the API provides one.

HTML CSS Grid JavaScript Fetch API Open Library API
Open live project ↗ Inspect source code ↗
01 / USER FLOW

How a search works

  1. A visitor enters a book title, author or subject.
  2. The form listens for a submit event.
  3. JavaScript sends an encoded query to Open Library.
  4. The response is converted from JSON.
  5. The first twelve available results are displayed.
  6. The interface shows a message when there are no results or a request fails.
02 / IMPLEMENTATION

Handling search input and results

const response = await fetch(
  "https://openlibrary.org/search.json?q=" +
  encodeURIComponent(query) +
  "&limit=12"
);

if (!response.ok) {
  throw new Error("Search failed.");
}

const data = await response.json();

I used encodeURIComponent() so spaces and special characters in a search query are safely included in the request URL.

03 / DATA PRESENTATION

Making results readable

  • Titles and author information are displayed in separate cards.
  • Missing author or publication details receive fallback text.
  • Cover images are requested only when a cover ID is available.
  • The escapeHTML() function escapes API text before it is inserted into the result markup.
  • The status area communicates loading, result count, empty results and connection errors.

WHAT I LEARNED

This project helped me connect form submission, URL encoding, API requests and dynamic result rendering in one complete user flow.

NEXT ITERATION

I would add pagination, a visible clear-search action, better handling for unavailable cover images and the ability to show more than one author.

CASE STUDY 03 / WEEK 08

Student Registration.

Designing a form that explains errors instead of hiding them.

Individual coursework

THE PROJECT

Validation with clear feedback.

I developed a student registration form that checks user input before showing a successful validation message.

The form combines built-in HTML constraints with JavaScript validation. It checks required information, input patterns, password confirmation and the user's agreement to the terms.

HTML5 Forms JavaScript Regular Expressions Constraint Validation ARIA
Open live project ↗ Inspect source code ↗
01 / VALIDATION RULES

What the form checks

  • Name is required and must contain at least two characters.
  • Student ID must contain exactly nine digits.
  • Email must use a valid email format.
  • Phone number must match the configured Korean mobile number pattern.
  • Password must contain at least eight characters.
  • Confirmation password must match the original password.
  • A course must be selected and the terms checkbox must be checked.
02 / IMPLEMENTATION

Custom validation feedback

field.setCustomValidity(error);

field.setAttribute(
  "aria-invalid",
  String(Boolean(error))
);

const errorElement = document.getElementById(
  field.id + "-error"
);

if (errorElement) {
  errorElement.textContent = error;
}

The validation function sets a custom error message, updates the field's invalid state and places feedback beside the related input.

03 / ACCESSIBILITY

Helping users understand mistakes

  • Inputs use associated labels.
  • Error messages are connected through aria-describedby.
  • The field's aria-invalid state is updated after validation.
  • A live status area announces the form result.
  • The first invalid field receives focus when submission fails.

WHAT I LEARNED

Validation should tell people how to fix a problem. A form should not simply reject an input without explaining what went wrong.

IMPORTANT LIMITATION

This is a front-end validation exercise. It does not create a real account, connect to a database or store submitted registration data. The success message is a browser-side demonstration.

CASE STUDY 04 / TEAM PROJECT

FindIt AI — Lost & Found.

Building a lost-and-found discovery experience with a teammate.

Collaborative project · With Alisher

THE PROJECT

Making lost-and-found discovery easier.

FindIt AI is a front-end lost-and-found discovery experience created collaboratively with Alisher. It provides a responsive interface for exploring lost-and-found categories and browsing a global discovery experience.

The project includes an interactive map, illustrative sample listings, local photo stories and search/report interface previews. We built the published interface using React, TypeScript and Vite.

React TypeScript Vite Responsive Design GitHub Pages
Open live project ↗ Inspect source code ↗
01 / FEATURES

What the project includes

  • Responsive lost-and-found interface for different screen sizes.
  • Global discovery categories and illustrative sample listings.
  • Interactive global map with 26 city hotspots across 24 countries.
  • Local cultural photo stories with source credits.
  • Search and report interface previews.
02 / TECHNOLOGY

How the application is built

  • React: used to build the interactive front-end interface.
  • TypeScript: used for the application's typed JavaScript code.
  • Vite: used for development and production builds.
  • GitHub Pages: hosts the published static website.
  • GitHub Actions: builds and deploys the frontend when changes are pushed to the main branch.
03 / COLLABORATION

Working as a team

  • Team members: Muhammadali Manopov and Alisher.
  • Project type: collaborative front-end development.
  • My role: co-developer working on the project with Alisher.
  • Shared goal: create a responsive and accessible lost-and-found discovery experience.

WHAT I LEARNED

This project gave me experience working on a larger front-end application with another developer. It also exposed me to a React and TypeScript workflow beyond my individual HTML, CSS and JavaScript coursework.

IMPORTANT DEMO LIMITATION

The published GitHub Pages version is a static front-end demo. Map hotspot counts and sample listings are illustrative. It does not include a hosted API, database, authentication service or live AI matching backend.
